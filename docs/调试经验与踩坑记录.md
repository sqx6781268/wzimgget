# 调试经验与踩坑记录

> 按"症状 → 根因 → 修复"整理，均为本项目实测案例，供后续 WZ 解析工作复用。

## 案例 1：长字符串乱码 + 后续解析神秘失步（最隐蔽）

**症状**
- 大部分文件、大部分节点解析正常；短属性名（origin/icon/price…）全部正确；
- 个别长字符串（`_outlink`、`desc`）解出乱码，且乱码**从第一个字符就错**；
- 乱码字符串之后同文件的所有内容（包括之前能解对的引用字符串）开始失步或解错；
- 不同文件表现不一致：小文件全对，大文件从某处开始崩。

**根因**
密钥流按需扩容函数 `ensure(n)` 扩容时新建了更大的数组，却**没把旧密钥流复制进前缀**，
链式加密以全零块作为前驱继续生成 → 从第一个扩容边界起所有密钥字节全错。
短字符串恰好落在首块（16 字节）内所以正常，造成"部分正常"的迷惑假象。

**修复**
```go
if start > 0 { copy(newKeys[:start], k.keys) }
```
**教训**：任何"按需生成长流"的代码，扩容路径必须有独立测试（先解短串触发小容量，再解长串）。
此一个 bug 修复后，Mob/Item 的全部失败文件同时恢复正常。

## 案例 2：`[:-6]` 切片越界 panic

**症状**：解 ANSI 字符串时 `negative slice index`。
**根因**：长度首字节为 sbyte 负数，忘记 `size = -size` 取反。
**修复**：`size==-128 ? 读int32 : size=-size`。注意 UTF-16 分支的 `127` 同理。

## 案例 3：zlib 数据被误判为"旧式加密块"

**症状**：部分 NPC 图标报 `非法数据块长度 2632833656`（一个巨大的 int32）。
**根因**：只认 `78 9C` 一种 zlib 头；`78 DA`（最高压缩级）走了加密块分支，
把 deflate 数据头 4 字节当块长读。
**修复**：按 zlib 规范校验：`b[0]==0x78 && (be16(b)%31==0)`。

## 案例 4：Go 1.27 编译错误 `image/bmp: not in std`

**根因**：Go 1.27 标准库移除 `image/bmp`。
**修复**：手写 BMP 解码（24/32bpp、无压缩、自底向上/负高、stride 4 对齐）。
**教训**：跟进新版 Go 时先查"removed from std"清单。

## 案例 5：flag 包吞掉位置参数后的选项

**症状**：`extract <data> -out X` 中 `-out` 不生效（输出写到了默认位置）。
**根因**：Go `flag.Parse` 遇到第一个非选项参数即停止解析其后所有选项。
**修复**：手动预扫描 args 分离位置参数与选项，保证任意顺序可用。

## 案例 6：解析中途出错导致整棵属性树丢失

**症状**：文件后段解析失败时，前段已解好的树也拿不到，无法 dump 定位。
**修复**：
1. `extractValue` 在读出属性名后**立即** `parent.Children = append(...)` 再解析值；
2. panic/recover 记录 `p.pos`，按"解析进度最深"的密钥返回部分树；
3. 节点记录 `AtOff`（名标记偏移），dump 输出 `@偏移`，与 hexdump 直接对照。

## 方法论：定位失步的标准流程

1. `WZTRACE=1` 逐 token 打印（位置/标记/长度/解码结果/上下文 16 字节十六进制）；
2. 找**第一个**解码异常的 token（注意区分"位置对但内容错"=解密问题，
   "位置都不对"=长度计算问题）；
3. `xxd -s <off> -l 32` 对照原始字节，与 WzComparerR2 源码逐字段核对；
4. 若怀疑密钥流，用能解对的短串与解错的长串对比它们所用的密钥流下标区间。

## 有效但值得记录的验证手段

- 用两个参考版本（WzComparerR2 master 与 v80315）交叉比对 Canvas 布局，确认数据是旧版形态；
- 独立 .img 无需 versionHash 爆破（MapleLib 的 WzFile 那套 0..32767 试版本逻辑不适用）；
- 调试小工具（如打印各 IV 下根串解密结果的 debug 程序）用完即删，避免污染主工程。
